# Microsoft 365 Outlook으로 PO 보내기

회사 도메인 DNS를 변경하지 않고, 각 본사 담당자가 자신의 Microsoft 365 계정을 연결해 PO를 발송합니다. 직원의 메일 비밀번호·Microsoft 앱 비밀키를 사이트에 입력하지 않습니다. 발송한 메일은 해당 계정의 Outlook 보낸 편지함에 저장하도록 요청합니다.

## 관리자가 한 번 준비할 것

1. [Microsoft Entra 관리 센터](https://entra.microsoft.com)에 회사 Microsoft 365 계정으로 로그인합니다.
2. **앱 등록 → 새 등록**을 선택합니다. 이름은 `SIG 생산관리 PO` 등으로 지정하고, 지원 계정은 **이 조직 디렉터리의 계정만(단일 테넌트)**을 선택합니다. 새 등록 권한이 없으면 회사 Microsoft 365 관리자에게 앱 등록을 요청합니다.
3. 앱의 **인증 → 플랫폼 추가 → 단일 페이지 애플리케이션(SPA)**에 다음 리디렉션 URI를 정확히 등록합니다.

   ```text
   https://sig-td.vercel.app/outlook-callback.html
   ```

   이 URI는 별도 콜백 문서입니다. 메인 로그인 주소로 바꾸거나 끝에 슬래시를 추가하지 않습니다. 개발 주소를 실제로 사용할 때만 해당 주소의 `/outlook-callback.html`도 별도로 등록합니다.
4. **API 권한 → 권한 추가 → Microsoft Graph → 위임된 권한(Delegated)**에서 **User.Read**, **Mail.Send**를 설정합니다. 사이트는 로그인한 사람의 메일함으로만 보냅니다. 조직 정책이 관리자 동의를 요구하면 회사 관리자가 승인해야 합니다.
5. 앱 **개요**에서 **애플리케이션(클라이언트) ID**와 **디렉터리(테넌트) ID**를 확인합니다. 두 값은 공개 식별자이며 Object ID와 다릅니다.
6. 사이트에 관리자 계정으로 로그인하고 **품번 상세 → PO → 회사 Microsoft 365 설정**을 엽니다. 위의 두 ID와 변경 사유를 입력하고 **Microsoft 설정 저장**을 누릅니다.

SPA의 인증 코드 + PKCE를 사용하므로 Client Secret은 만들지 않습니다. 각 직원이 같은 회사 공용 앱을 자신의 계정으로 승인하며, 회사 DNS나 직원별 Resend 계정은 필요하지 않습니다. 회사 보안 정책의 앱 등록·사용자 동의 제한은 그대로 적용됩니다.

## 담당자가 연결하고 발송하기

1. 사이트에 본인의 승인된 본사 계정으로 로그인합니다. 사이트 가입 이메일과 Microsoft 메일함의 회사 이메일이 같아야 합니다.
2. **품번 상세 → PO → Outlook 연결**을 누릅니다.
3. Microsoft 창에서 본인 회사 계정으로 로그인하고 표시되는 권한을 승인합니다.
4. 화면에 연결된 이메일이 본인 주소인지 확인합니다. 연결만으로는 메일이 발송되지 않습니다.
5. PO의 프로젝트·생산 차수·수신인·요청 납기·본문을 확인하고 초안을 저장합니다.
6. **PO 메일 발송 → 발송 확인**을 누릅니다. 확인 창에 발신자와 수신자가 표시됩니다.
7. 사이트의 Microsoft 접수 결과와 Outlook 보낸 편지함을 확인합니다. 실제 받은편지함 도착은 별도로 확인합니다.

처음 시험 수신자는 사용자가 지정한 `made@adererror.com`입니다. 시험임을 제목·본문에 명시하고 실제 업체 발주를 요청하지 않습니다.

## 처리 기준

- 서버가 사이트 로그인과 승인·활성 본사 권한을 확인하고, Microsoft Graph에서 실제 연결 메일함을 확인합니다. 다른 직원 주소를 임의의 발신자로 입력할 수 없습니다.
- Microsoft 토큰은 MSAL의 브라우저 세션 캐시와 단일 발송 요청에 사용합니다. 데이터베이스에 Microsoft 토큰·비밀번호·앱 비밀키를 저장하지 않습니다. **Outlook 연결 해제**는 현재 브라우저의 연결 캐시를 해제하며 사이트 로그인이나 Outlook 전체에서 로그아웃하지 않습니다.
- Outlook의 사진·PDF 첨부는 **최대 2MB**입니다. 서버에서 스타일 소속·접근 권한·파일 크기를 확인한 뒤 발송을 시작합니다. 더 큰 파일은 현재 경로에서 발송하지 않습니다.
- Microsoft의 HTTP 202와 실제 `request-id`를 **Microsoft 접수 추적 ID**로 보존합니다. 이를 이메일 메시지 ID나 수신·열람 증명으로 표시하지 않습니다.
- PO의 발송 방법·발신자·제목·본문·수신자·납기·시도를 보존합니다. 시도한 PO를 다른 발송 서비스나 다른 직원 계정으로 재전송하려면 새 PO로 작성합니다.
- 결과가 불확실한 `발송 요청 중`·`접수 여부 확인 필요` 상태는 자동 재발송하지 않습니다. 보낸 편지함과 발송 이력을 먼저 대조합니다.
- 기존 Resend 발송과 과거 이력은 유지합니다. Microsoft 설정이 완료된 새 PO는 Outlook을 사용하고, 이미 시도한 PO는 기존 발송 방법을 유지합니다.
- 업체가 확인할 PO와 생산 동의의 기존 권한·납기·생산 차수 보호는 유지합니다.

## 배포 설정

기존 001~011 SQL이 적용된 프로젝트에 [012_outlook_po_email.sql](../supabase/migrations/012_outlook_po_email.sql)을 적용하고 최신 앱과 `send-po-outlook` 함수를 배포합니다. 기존 초기 SQL은 다시 실행하지 않습니다. 012는 기존 업무 자료를 초기화하지 않습니다.

```bash
supabase functions deploy send-po-outlook --project-ref YOUR_PROJECT_REF --no-verify-jwt
```

함수는 `PO_ALLOWED_ORIGINS`와 Supabase 기본 제공 서버 환경을 사용합니다. 이 Microsoft 방식에는 `RESEND_API_KEY`, `PO_FROM_EMAIL`, Client Secret이 필요하지 않습니다. Gateway JWT 검증을 끄더라도 함수 내부에서 Supabase Auth·현재 프로필·Microsoft 메일함을 검증합니다.

Vercel은 `/outlook-callback.html`을 앱의 `index.html`로 바꾸지 않고 그대로 제공해야 합니다. 저장소의 `vercel.json`에 해당 예외가 포함되어 있습니다.

## 현재 확인 범위

코드·로컬 데이터베이스·가짜 Microsoft 응답을 사용한 검증과 실제 계정 발송 시험은 구분합니다. 회사 앱 등록과 본인 Microsoft 로그인 승인이 끝나기 전에는 실제 Outlook 발송을 완료했다고 판단하지 않습니다.

2026년 10월 28일 첫 회사 계정의 실제 PO 발송에서 Microsoft 접수 추적 ID·발신자·첫 시도 성공 기록을 운영 DB로 확인했습니다. 사용자가 실제 메일 수신을 확인했습니다. 다른 담당자도 각자 계정을 연결해 사용하며, 다른 직원 계정 전체의 실제 발송을 시험한 것은 아닙니다.
