## 2026-11-09 발주 예산 M·O 산식 수정과 N 확인 제거

전체 **단위·로컬 DB·서버 테스트 1,676개(91파일)**, **npm run build(TypeScript·Vite)**, 예산·원가 업로드·고정 을지의 **브라우저 20개 시나리오**가 통과했습니다.

- 새 첨부 최종 예산 파일에서 발주 U=동일 예산 코드의 원가 AG 합계, W=U/TTL을 확인했습니다. 원가 AF는 일반 항목에서 변동단가 우선 × 요척량, 공용비용에서 금액/기획수량, AG는 AF×기획수량입니다. 업로드한 장당 항목을 총예산으로 취급하고 다시 수량으로 나누던 계산을 수정했습니다.
- 사이트 O는 장당 생산 원가, M은 O×생산 수량입니다. 소수 6자리 장당 원가를 반올림하지 않고 정수 수량을 곱합니다. 변동단가 0원 우선, 공용비용 1회 배분, 기존 수동 총액 보존, 미등록과 0원을 검증했습니다.
- 같은 프로젝트·품번의 복수 차수는 수량을 합산하고, 업체별 필터·그룹과 시즌 한도 잔액도 같은 산식을 사용합니다. 서로 다른 프로젝트 ID의 수량과 원가를 섞지 않습니다. 계정 권한과 운영 원본은 바꾸지 않습니다.
- 발주표 N 사후원가 확인을 제거했습니다. Excel N은 빈 열로 숨겨 M/O 위치를 유지하고 CSV도 N 확인 내용을 제외합니다. M=IF(O="","",O×J) 수식·정확한 계산 결과, O 직접 장당 값, FA 기존 O/P/Q 수식·부가세·합계와 원가 U=Q×S를 확인했습니다.
- 사후 원가 기록·변경 이력은 유지하며 사후 원가 미등록만으로 종결을 막지 않습니다. PC·390px 모바일, 실제 업로드→집계→CSV/Excel 다운로드와 FA 읽기 전용·동시 수정 보호를 확인했습니다.

추가 SQL은 없습니다. 웹 배포 후 기존 원가를 다시 조회하면 새 산식으로 계산합니다. 운영 원가·PO·입출고·마감·지급 기록을 수정하거나 파일을 재업로드하지 않습니다.

## 전체 품번과 등록·수량 적용 통합

F열의 14자리 전체 품번은 그대로 우선 읽고, 컬러를 별도 입력하지 않습니다. 기존 전체 코드와 기존 기본 품번·생산 컬러 구조를 연결합니다. 사용자는 F가 12자리 기본 품번일 때 B 예산코드에서 전체 품번을 자동 인식하는 보완도 승인했습니다. B는 정확한 A+F+두 자리 일치일 때만 사용하고 I는 읽지 않습니다. 전체 품번 표시에서 BKBK가 중복되지 않는지 검증했습니다.

신규 한 건은 등록 정보가 자동으로 열리고 **품번 등록 및 수량 적용** 한 번으로 연속 처리합니다. 공장의 ㈜/(주)와 공백 차이는 유일하게 일치할 때만 연결하며 AO 입고예정일을 출처와 함께 기준 납기로 제안합니다. 실제 첨부 CP949 CSV에서 전체 품번 `BP06FYDW0101BK`, 납기 2026-10-14, 총 4,138개 payload를 로컬 검증했습니다. 운영에 실제 업로드하지 않았습니다.

최종 브라우저 검증은 자동 전체 품번·등록·4,138개 적용, 잘못된 합계의 등록 전 차단, 실제 두 탭의 기존 오더 변경 시 등록 전 재검증 요구, 파일 형식 변경 시 준비한 등록 계획 취소, 모바일·다수 행 입력을 포함합니다. 저장 RPC 성공 후 조회 실패와 수량 적용 실패를 부분 완료로 구분합니다. 기존 스타일·원본 기록의 버전은 파일을 처음 읽은 값을 유지합니다. 추가 SQL은 없습니다.

## 최신 기본 품번 CSV 업로드 오류 수정

다시 첨부한 같은 이름의 CSV는 3,165바이트, CP949, 3행·153열이고 제목은 1행, 유효 데이터는 2행입니다. F가 `BP06FYDW0101BK`에서 **컬러 없는 `BP06FYDW0101`**로 바뀌었습니다. 기존 검사는 컬러 접미사가 없으면 수량을 읽기 전에 중단하여, 정상 수량이 0처럼 보였습니다.

- 실제 첨부파일을 앱 파서로 열어 **AQ~AV 60 / 384 / 626 / 1,296 / 1,162 / 610, AY 4,138**을 확인했습니다. 기본 품번 + 명시한 BK로 로컬 등록 계획·수량 payload를 검증했으며 운영 DB에 업로드하지 않았습니다.
- 품번 매칭 전에 수량을 읽어 미등록·컬러 미지정 행에도 실제 파일 수량을 표시합니다. 등록된 컬러가 하나면 연결하고, 여러 컬러이거나 미등록 품번이면 행별 컬러를 직접 입력해야 저장할 수 있습니다.
- 원본 F는 기본 품번 그대로 보존하고 I열을 읽지 않습니다. 같은 F의 여러 행은 직접 지정한 컬러별로 연결하며 다른 컬러·실출고·실입고는 변경하지 않습니다.
- 잘못된 컬러·음수·합계 불일치는 계속 차단합니다. 기존 컬러 포함 F 형식과 7행 머리글 파일을 유지합니다. 30행에서 더 보기를 누른 뒤 26번째 이후 컬러를 입력해도 펼친 행과 입력값이 유지되는지 검증했습니다.
- 이번 변경에는 추가 SQL이 없습니다. 사용자 보고에 따르면 005가 적용되어 있으며, 운영 배포의 이전 `0a5348d` Ready는 사용자 화면에서 확인했습니다.

## 제공된 을지와 수동 원가 검증

실제 **`SIG_을지.xlsx`의 `대금지급(을)` 시트**를 확인했습니다. 머리글은 2행, 데이터 원형은 3행이고 `거래명세표` Excel 표가 있습니다. 원본의 개인 작성자·로컬 파일 경로를 제거한 빈 양식을 앱 자산으로 포함했습니다. 지정 열을 자동 작성하며 매번 원본을 다시 올릴 필요가 없습니다.

- A 프로젝트 코드, C 현재 실 입고일, D 현재 담당 공장, I 품번+컬러, N 본사 입력 원가, O=1
- P 현재 PO 오더 수량, Q=P, R 현재 실제 입고 수량, S 원단 `YDS` / 제품·라벨 `EA`, W 현재 담당자
- 사용자가 확인한 대로 **T=N×R, 부가세 제외**. U는 T×10%, V는 T+U이며 원본의 수식과 계산 결과 캐시를 유지합니다.
- 원가를 기존 마감 금액에서 역산하거나 다른 생산의 원가를 공통값으로 자동 배정하지 않습니다. 본사·관리자가 생산 스타일·컬러별로 직접 입력·수정하며, 미입력 null과 명시적 0원을 구분합니다.
- 원본 표·필터·검증 범위·요약 합계를 데이터 행 수에 맞춰 확장하고, 원본 서식·인쇄 바이너리·custom XML 등 변경할 필요 없는 ZIP 구성은 바이트 단위로 비교했습니다. 오래된 계산 체인 참조는 제거하고 재계산을 요청합니다.
- 검색·컬러 필터에 포함되지 않은 컬러를 임의로 내보내거나 그 컬러의 미입력 원가 때문에 다운로드가 차단되지 않는지 확인했습니다.
- 본사 직원의 저장과 전용 이전/이후 값·사유 이력, 공장/미승인/비활성 계정 차단, 오래된 버전·없는 컬러·삭제 스타일 거부를 실제 PostgreSQL로 실행했습니다. 공장이 보는 일반 감사 기록은 단가·민감 사유가 없는 요약만 포함합니다.

- 다운로드한 파일을 ExcelJS와 Python openpyxl로 각각 다시 열어 표 범위·입고 날짜·12개 지정 열·U/V 수식·계산 결과·합계 및 원본 인쇄 바이너리를 대조했습니다. 실제 Windows Excel의 렌더링·인쇄는 이 환경에서 실행하지 않았습니다.

## 가입 요청 경로 오류 검증

SDK가 `/rest/v1/`이 붙은 설정 주소에 `/auth/v1/signup`을 덧붙이는 동작을 재현했습니다. 프로젝트 기본 주소와 알려진 서비스 루트 주소를 정규화하고, 지원하지 않는 경로·쿼리·접속 정보는 오류로 안내합니다. 실제 Supabase SDK에 테스트용 fetch를 주입해 가입 `/auth/v1/signup`, 로그인 `/auth/v1/token?grant_type=password`, 암호 재설정 `/auth/v1/recover` 요청 경로를 확인했습니다. 이 검증은 실제 네트워크나 운영 사용자 계정을 사용하지 않습니다.

사용자가 제공한 Vercel 사이트의 HTML·배포 설정 확인은 실행 환경의 네트워크 프록시가 403으로 거부하여 수행하지 못했습니다. 실제 환경변수 값은 직접 확인하지 못했습니다. 이후 사용자 제공 화면에서 최신 배포 Ready·가입 요청 수락·인증 메일 수신, 관리자 업무 화면 및 SQL의 `admin / approved=true / email_confirmed_at` 값을 확인했습니다. 이는 사용자가 제공한 화면의 관찰이며, 이 실행 환경에서 운영 계정에 로그인하거나 직접 DB를 조회한 검증은 아닙니다.

## 인증 메일 재발송과 복귀 주소

`otp_expired`가 포함된 실제 오류 형태를 쿼리·해시로 입력해 한국어 안내를 확인했습니다. 정상 토큰·PKCE·복구 URL은 오류로 오인하거나 제거하지 않습니다. 오류 설명의 임의 HTML·민감 문자열은 화면에 반영하지 않습니다. Supabase SDK의 재발송 요청을 mock fetch로 검증하여 POST `/auth/v1/resend`, `type=signup`, 이메일과 `redirect_to`를 확인했습니다. API 오류·메일 제한은 성공으로 처리하지 않습니다.

별도의 로컬 Vite 서버에 테스트 전용 공개 설정을 주입하고 Chromium에서 실제 로그인 UI를 점검했습니다. 모든 외부 Auth 응답은 Playwright로 가로채며 실제 이메일을 보내지 않았습니다. 이메일만 입력한 재발송, 수락 안내와 60초 중복 요청 차단, HTTP 429 실패 안내, 만료 callback 및 390px 화면을 확인했습니다.

사용자 화면의 `localhost:3000/#error=access_denied&error_code=otp_expired`는 잘못된 인증 복귀 주소와 만료·사용된 링크를 보여 줍니다. Supabase **Authentication → URL Configuration**에서 운영 **Site URL**과 **Redirect URLs**를 등록한 뒤 새 메일을 받아야 합니다. 이 서버 설정을 앱 코드가 대신 수정하지는 않습니다. 실제 Site URL 설정 변경과 새 메일의 인증 흐름은 이 실행 환경에서 직접 검증하지 않았습니다. 사용자 SQL 화면에는 이메일 확인 시각이 기록되어 있었습니다.

추가 보완 후 `npm run build`와 스타일 등록·샘플·파일 저장 시나리오 1개를 재실행해 통과했습니다. 새 샘플을 아직 저장하지 않았을 때 코멘트·파일 첨부를 차단하는 브라우저 점검도 통과했습니다(미등록 코멘트·고아 파일 생성 없음).

## PostgreSQL 검증 내용

PGlite의 실제 PostgreSQL 엔진에서 배포용 SQL 마이그레이션을 실행합니다. Supabase 전용 `auth.uid()`, Auth 사용자 테이블, Storage 테이블과 역할은 테스트용으로 구성했습니다. 실제 Postgres의 GRANT, RLS, SECURITY DEFINER RPC와 JSON 검증을 실행했으며, hosted Supabase의 네트워크·Auth·파일 API를 실행한 것은 아닙니다.

- 익명·미승인·비활성 사용자 접근 거부, 가입 메타데이터로 관리자 권한 취득 불가
- 스타일 직접 수정·삭제 차단, 승인 계정의 역할·공장에 따른 RPC 검증
- 배정되지 않은 공장의 스타일·프로젝트·코멘트·파일·감사 이력 차단
- 공장의 본사 요청·기준 납기·최종 컨펌·입고 수량·정산 수정 차단
- 본사 직원의 출고·입고 수량 수정 차단, 관리자의 수량 입력 허용
- 버전 충돌로 오래된 저장 거부, 기존 샘플·생산 이력 제거 및 차수 변경 차단
- 날짜 변경 사유, 이전/변경 값 감사 기록, 변경·삭제 이력 보존
- 형식·사이즈·음수 수량·중복 및 비정상 식별자 검증
- 실제 프론트엔드 예시 구조의 SQL 저장과 공장 재배정 후 이전 공장 접근 차단
- 파일 경로·형식·용량·메타데이터 및 private Storage RLS
- 담당자 디렉터리에 접근 가능한 스타일의 본사 이름·ID·역할만 노출
- 새로 등록·수정한 샘플의 서버 시각 기록, 클라이언트 시각 위조 방지
- 예시 SQL의 반복 실행 및 공장·프로젝트 수정 이력
- 대표 이미지의 승인된 관리자·본사 직원만 변경 허용, 공장 배정별 조회와 직접 쓰기 차단
- 타 스타일·샘플 사진·PDF의 대표 이미지 지정 거부, 컬러 검증과 원본 첨부파일 보존
- 이미지 연결 해제 후에도 버전을 유지하여 과거 편집의 덮어쓰기 차단, 변경 전후 값·사유 감사 기록

## 아직 실행하지 않은 검증

실제 Supabase URL·공개 키·테스트 계정이 제공되지 않아 다음 작업은 **미실행**입니다.

- hosted Supabase Auth 회원가입·이메일 인증·실제 로그인·비밀번호 재설정 메일
- hosted Postgres와 프론트엔드 간 실제 저장·조회, 서로 다른 사용자·기기 사이 Realtime 전달
- 실제 Supabase Storage 업로드·다운로드 및 실제 JWT에 따른 파일 접근
- 실제 운영 데이터·업무자 인수 테스트, 대량 데이터 성능·백업 복원·부하 테스트
- Vercel 실제 배포·운영 도메인 리다이렉트
- 기존 클라우드 프로젝트의 `005_workflow_refinements.sql` 적용, 실제 사용자 간 추가 업무·이미지 전달과 동시 PostgreSQL 세션의 잠금 동작
- Resend 실제 발송·메일 수신·반송, Edge Function 배포 및 실제 server Secrets
- 회사 CSV의 운영 데이터 반영·실제 원가 입력 및 현업 인수, 실제 Windows Excel 인쇄

대표 이미지 SQL은 PGlite에서 기존 001 이후 002를 적용해 검증했습니다. SQL 충돌 검사는 오래된 버전을 순차적으로 제출하는 방식이며, 별도 운영 세션을 동시에 연결한 검증은 아닙니다. 브라우저의 두 탭 동시 편집은 체험 모드에서 실제로 실행했습니다.

체험 모드에서의 저장·역할 전환·탭 동기화 테스트를 실제 사용자 인증 또는 서로 다른 컴퓨터 간 협업 성공으로 해석하지 않습니다. 실제 연결 후 [구현 범위 문서](IMPLEMENTATION.md)의 서비스 검증 절차를 실행해야 합니다.

## 현재 진행 단계별 집계와 통합 목록

사용자는 샘플과 메인 생산을 한 목록에서 계속 보되 집계만 현재 단계별로 구분하도록 요청했습니다. 목록은 유지하고 샘플 진행 단계는 샘플 집계, 메인 생산 단계는 생산 집계에 포함합니다. 등록·승인 상태에 생산 수량이 있으면 생산으로, 수량 없는 신규 등록은 샘플 대기로 분류합니다. 과거 샘플 이력의 존재만으로 진행 중 샘플에 포함하지 않고 완료·승인 후 수량이 없는 품번은 진행 집계에서 제외합니다. 본사 전용 원본 테이블을 분류 기준으로 쓰지 않아 공장도 같은 기준을 따릅니다.

이 변경 후 `npm run build`, 기존 도메인 37개, 브라우저 3개(기존 대시보드·스타일 등록, 새 단계별 집계)가 통과했습니다. 다섯 품번이 양쪽 목록에 유지되고 샘플 2·생산 3으로 나뉘는 것을 확인했습니다. 샘플 품번을 실제 화면에서 생산 단계로 저장한 뒤 샘플 1·생산 4로 바뀌고 과거 샘플·생산 이력이 그대로 남는지 검증했습니다. 추가 SQL은 없습니다.


## 복수 필터·가공/검사 을지 추가 검증

- 프로젝트 두 개 OR 선택 + 공장·제품 AND 조건, 검색 중 숨겨진 선택 유지, 전체보기/선택없음 구분, 필터별·전체 초기화, 390px 팝업 범위와 Escape 초점 복귀
- 달력 프로젝트·종류·제품 복수 선택을 월간/주간·선택일·7일 집계에 동일하게 적용, 공장 계정에서 협력업체 휴가 내용과 선택지 비노출
- 전체 스타일 보기에서도 BK/OW 선택 시 화면 합계·CSV·Excel 생산 행에 NV가 추가되지 않고 원본 스타일·수량은 보존
- 브라우저에서 실제 파일을 내려받아 중화라벨 2행·자수 1행·선택 컬러 품질검사 1행을 ExcelJS로 다시 읽고 지정 업체명과 품질검사 업체 빈 셀·N 단가 빈 셀·P/Q/R 수량·L 작업명을 대조
- 라벨 입고 수량 빈칸, 자수 등록 완료 수량만 사용, 검사 완료 확인이 없으면 수량 빈칸, 작업을 컬러 수만큼 복제하지 않음
- 처리 금액과 합계는 미작성 값이 남아 있으면 빈칸인 수식이며 메인 제품 원가·입고 수량을 대신 사용하지 않음. 원본 OOXML·표 범위·인쇄 설정 보존 및 기존 제품 필수 정보 검증 유지
- 등록 내역이 없으면 작성 항목별 다운로드 차단·안내, 품질검사 업체 셀을 담당자가 나중에 직접 입력할 수 있음

권한·SQL 스키마 변경 없이 기존 저장 자료를 조회해 화면과 파일을 생성합니다. 새 SQL은 없습니다.
