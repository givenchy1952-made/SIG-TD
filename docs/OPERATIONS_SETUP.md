# 추가 업무 기능 설정·사용 안내

오더 Excel 가져오기, 프로그램에서 PO 메일 발송, 부분 출고, 실제 마감 양식 채우기, 직원별 담당 공장 배정, 휴가·런칭 일정, 중화 라벨, 비와이 자수 기능의 사용 절차입니다. 기본 설치·계정 승인·Vercel 배포는 [README](../README.md)를 먼저 확인하세요.

## 데이터베이스 업데이트

| 현재 프로젝트 상태 | 적용할 SQL |
| --- | --- |
| 새 Supabase 프로젝트 | `001_initial.sql` → `002_style_images.sql` → `003_operations.sql` 순서로 각각 한 번 |
| 001만 적용 | 002 → 003만 각각 한 번 |
| 001·002 적용 완료 | **003만 한 번** |
| 001·002·003 적용 완료 | SQL 재실행 없이 앱 버전·함수 설정 확인 |

Supabase SQL Editor에서 [003_operations.sql](../supabase/migrations/003_operations.sql)을 실행한 후 새 앱을 다시 배포하세요. 기존 001·002를 다시 실행하지 않습니다. 003은 기존 스타일·샘플·이미지 테이블을 초기화하지 않는 증분 마이그레이션입니다. 적용 전에는 프로젝트의 백업·변경 관리 절차를 따르세요.

003이 없는 기존 프로젝트에서도 기본 샘플·생산 화면은 열립니다. 추가 업무 등록은 설정 안내와 함께 차단합니다. SQL 적용 후 앱에서 다시 불러오거나 새로고침하세요. 파일 가져오기의 사전 분석과 양식 미리보기는 실제 저장과 별개입니다.

## Excel 오더 수량 가져오기

승인된 관리자·본사 직원이 사용할 수 있습니다. 지원 파일은 암호화되지 않은 `.xlsx` 또는 **UTF-8 CSV**, 최대 10MB입니다. Excel은 최대 30개 시트, Excel·CSV 모두 시트당 10,000행·200열을 지원합니다. 파일은 브라우저에서 읽고 검증합니다. 큰 Excel은 **첫 탭 ORDER QTY만 선택하여 CSV UTF-8로 저장**한 뒤 가져오세요. CSV에는 이미지·다른 시트가 포함되지 않습니다.

1. 등록된 스타일과 컬러를 먼저 준비합니다. 품번은 컬러를 포함한 전체 품번 또는 기본 품번 + 별도 컬러 열로 연결합니다.
2. 원본 파일을 선택하고 사용할 시트·머리글 행을 확인합니다. 자동 인식한 열도 반드시 확인하세요.
3. 가로 형식(XXS·XS·S·M·L·XL별 열) 또는 세로 형식(품번·컬러·사이즈·수량)을 선택하고 각 열을 연결합니다.
4. **기존 오더 교체** 또는 **기존 오더에 추가**를 고릅니다. 교체는 파일 수량으로 바꾸고, 추가는 현재 오더에 더합니다.
5. 변경 전·파일 수량·변경 후 수량과 모든 오류를 확인합니다. 기본적으로 중복 품번·사이즈와 누락 사이즈는 오류입니다. 합산·누락 0처리는 사용자가 명시적으로 허용할 수 있습니다.
6. 변경 사유를 입력하고 **검증된 오더 적용**을 누릅니다.

알 수 없는 스타일·컬러를 임의로 만들지 않습니다. 음수·소수·범위 초과 수량, 매칭 실패, 중복·누락 등 오류가 있으면 적용하지 않습니다. 수식 자체를 실행하지 않고 파일에 저장된 계산 결과만 읽습니다. 계산 결과가 없는 수식은 Excel에서 계산한 뒤 저장해야 합니다.

SIG 형식의 원본 참조 정보도 아래 설명에 따라 함께 저장합니다. 적용은 선택한 전체 변경에 대해 한 번의 서버 트랜잭션으로 처리합니다. 어느 스타일이든 미리보기 이후 버전이 바뀌거나 권한·형식 검증이 실패하면 **전체가 취소**됩니다. **최신 데이터로 다시 검증**한 뒤 수량을 대조하세요. 출고·입고 수량과 생산 체크리스트는 변경 대상이 아닙니다.

### SIG ORDER QTY 형식과 원본 참조

제공된 대용량 ORDER Excel은 파일 전달 용량 한도로 내용을 직접 분석하지 못했습니다. 실제 열 제목·데이터를 확인한 것으로 주장하지 않습니다. **ORDER QTY 시트의 UTF-8 CSV**를 준비하여 실제 원본과 대조해야 합니다. 일반 형식과 별도로 **파일 형식 → SIG ORDER QTY**를 선택하면 사용자가 지정한 다음 열 위치를 적용합니다.

| 원본 열 | 적용 |
| --- | --- |
| `F` | 전체 품번. 마지막 영문 두 자리를 컬러로, 나머지를 기본 스타일 코드로 매칭 |
| `AQ, AR, AS, AT, AU, AV` | 각각 `XXS, XS, S, M, L, XL` 오더 수량 |
| `AY` | 여섯 사이즈 합계와 대조하는 총수량 |
| `A, L, M, S, V, W, X, Y` | 원본 제목·값 그대로 보관하는 참조 정보. 의미를 추측해 이름을 바꾸지 않음 |

총 16개 열의 원본 제목·값, 파일명·시트명·행 번호를 오더 수량과 함께 보관합니다. 수량이 같아도 참조 정보가 다르면 변경 대상으로 표시합니다. 미등록 스타일·컬러는 오류이며 자동 생성하지 않습니다. 먼저 스타일·컬러를 등록하고 다시 검증하세요.

저장 후 스타일 상세의 **ORDER QTY 원본** 탭에서 등록 시점의 원본을 확인합니다. 승인된 본사는 `A/L/M/S/V/W/X/Y` 참조 값을 수정할 수 있습니다. `F`, `AQ~AV`, `AY`는 가져온 시점의 스냅샷으로 유지합니다. 실제 오더 수량을 수기로 바꿀 때는 **메인 생산**에서 수정합니다. 원본 참조를 편집했다고 오더 수량이 바뀌거나, 수기를 바꿨다고 가져온 당시 원본 수량이 바뀌지는 않습니다. `order_source_records`는 본사 전용이며 별도 버전·사유를 검사합니다.

## PO 메일 발송

승인된 관리자·본사 직원이 초안을 만들고 발송합니다. 외부 공장은 배정된 스타일의 이력을 조회합니다. 체험 모드에서는 초안과 이력을 살펴볼 수 있지만 실제 이메일을 발송하지 않습니다.

1. 스타일의 담당 공장과 PO 수신 이메일을 확인합니다.
2. **PO 작성**에서 PO 납기일·수신 이메일·제목·내용을 입력하고 변경 사유와 함께 **PO 초안 저장**합니다. 초안 저장은 발송이 아닙니다.
3. 저장된 내용의 납기·수신인·제목을 검토하고 **PO 메일 발송 → 발송 확인**을 누릅니다.
4. 접수 결과·서비스 접수 ID·시도 이력을 확인합니다. 납기는 서버가 실제 발송 제목·본문에 포함합니다.

PO에서 기존 스타일 첨부파일을 선택하면 서버가 권한을 확인해 **PDF·JPG·PNG·WEBP 파일 1개(최대 10MB)를 실제 메일에 첨부**합니다. 선택한 파일명과 수신인을 발송 전에 확인하세요. 파일이 없거나 접근·형식·용량 검증에 실패하면 성공 처리하지 않습니다. `.eml` 다운로드는 첨부파일이 없는 메일 초안 생성이며 실제 발송과 구분합니다.

| 서버 상태 | 화면 의미 | 다음 행동 |
| --- | --- | --- |
| `draft` | 초안·미발송 | 내용 확인 후 발송 |
| `sending` | 발송 요청 처리 중 | 중복 요청 금지, 실제 접수 결과 확인 |
| `sent` | **발송 접수** | 메일 서비스가 요청을 수락하고 접수 ID를 반환한 상태 |
| `failed` | 발송 실패 | 오류 원인 수정 후 허용된 동일 내용 재시도 또는 새 PO 작성 |
| `unknown` | 접수 여부 확인 필요 | 자동·사용자 재발송 차단, 서비스 관리자 대조 필요 |

`sent`는 수신자 편지함 도착·열람·공장 확인을 의미하지 않습니다. 스팸 분류·반송·배달 결과는 실제 메일 서비스에서 확인해야 합니다. 네트워크 시간 초과 등으로 결과가 불명확하면 `unknown` 또는 처리 중 상태로 남을 수 있습니다. 임의로 성공 처리하거나 중복 발송하지 말고, 메일 서비스 기록과 접수 ID·시도 일시를 대조한 뒤 신뢰할 수 있는 관리자 절차로 정리하세요. 자동 조정 화면은 제공하지 않습니다.

발송을 시도한 PO는 내용을 수정하지 않습니다. 정정은 **새 PO로 복사**하여 새 기록으로 작성합니다. 아직 발송을 시도하지 않은 초안만 보관할 수 있으며 원본·시도 이력은 남습니다.

### 실제 메일 서비스 설정

이 기능에는 Supabase Edge Function **send-po-email**과 Resend 계정의 API 키·검증된 발신 주소가 필요합니다. 클라이언트 공개 키와 별개의 **서버 전용 설정**입니다. 실제 자격정보가 없는 개발 검증에서는 메일 발송 완료로 처리하지 않습니다.

Supabase CLI를 설치·로그인한 뒤 저장소 루트에서 설정합니다. 예시 파일은 `supabase/.env.functions.example`입니다.

```bash
cp supabase/.env.functions.example supabase/.env.functions.local
```

복사한 로컬 파일에 다음 **서버 전용 세 값만** 입력하세요. 호스팅 함수의 `SUPABASE_` 기본 변수는 플랫폼이 제공하며 Secrets로 다시 설정하지 않습니다. 로컬 파일은 Git에 넣지 않습니다.

| 변수 | 설정 |
| --- | --- |
| `RESEND_API_KEY` | 발송 권한이 있는 Resend API 키 |
| `PO_FROM_EMAIL` | Resend에서 검증된 발신 주소. 예: `FIVE SPACE / SIG <po@YOUR_VERIFIED_DOMAIN>` |
| `PO_ALLOWED_ORIGINS` | 허용할 앱 origin을 쉼표로 구분. 예: `https://YOUR_APP.vercel.app,http://localhost:5173` |

origin에는 URL 경로·끝 슬래시·와일드카드 없이 프로토콜과 호스트·필요한 포트만 지정합니다. 운영 주소와 시험 주소를 실제로 쓰는 값만 등록하세요. Resend의 발신 도메인·주소 검증과 필요한 DNS 설정을 먼저 완료해야 합니다.

```bash
supabase secrets set --project-ref YOUR_PROJECT_REF --env-file supabase/.env.functions.local
supabase functions deploy send-po-email --project-ref YOUR_PROJECT_REF
```

`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`는 호스팅된 Supabase Edge Function의 기본 제공 환경을 사용합니다. `service_role`은 이 함수 서버 내부에서 결과 확정에만 사용하며 프론트엔드로 전달하지 않습니다. 키를 Vercel의 `VITE_` 변수·Git·로그·채팅에 넣지 마세요. 함수는 Resend의 `api.resend.com`으로 HTTPS 발송 요청을 보냅니다.

`supabase/config.toml`의 `send-po-email` 설정은 `verify_jwt=false`입니다. 이 함수는 각 요청의 Bearer 토큰을 **Auth 서버의 `getUser`로 직접 검증**하고, 사용자 JWT로 호출하는 DB RPC에서 승인된 본사 계정 권한을 다시 확인합니다. 따라서 Gateway JWT 설정과 별개로 인증을 강제합니다. 이 검증 코드를 제거하지 마세요. 제공된 config를 사용하지 않는 별도 배포 절차에서는 동일한 함수 설정을 적용해야 합니다.

배포 후 최신 앱을 열고 승인된 본사 시험 계정으로 PO 한 건을 작성합니다. 실제 수신인·제목·납기를 확인하고 명시적으로 발송한 뒤 Resend 접수 내역 및 수신함을 각각 확인하세요. 함수 배포·서버 Secrets 등록과 Vercel 클라이언트 배포는 서로 다른 단계입니다. 잘못된 origin·미검증 발신 주소·미등록 키는 성공 처리하지 않습니다.

## 차수별 부분 출고

외부 공장 또는 관리자가 컬러별 **출고 차수 추가**로 1차·2차 등의 실제 출고일, 운송장, XXS~XL 수량과 메모를 입력합니다. 본사 직원은 조회·다운로드할 수 있습니다. 기존 생산 화면의 입력 수량은 첫 차수 저장 시 **이전 입력 수량** 기준으로 보존하고, 유효한 차수별 출고만 더해 누적 실 출고를 계산합니다.

기존 수량을 다시 1차 출고에 복사하면 중복 합산될 수 있으므로 첫 저장 전에 기준 수량을 확인하세요. 기록을 정정할 때 원본을 제거하지 않고 사유와 함께 수정·무효 처리합니다. 무효 차수는 누적 합계에서 제외하되 이력은 남깁니다. 입고 수량은 기존대로 관리자만 입력합니다.

스타일·출고 차수 버전을 함께 검사합니다. 다른 사람이 수량이나 스타일을 먼저 저장하면 누적 합계를 덮어쓰지 않고 충돌을 안내합니다. 차수 기록이 시작된 컬러의 실 출고 합계는 차수 원장을 통해 관리하세요.

## 실제 을지 마감 양식 채우기

실제 을지 `.xlsx` 원본이 제공되지 않아 **을지 양식과 정확히 일치한다고 검증하지 않았습니다.** 임의 양식을 을지 양식으로 만들지 않습니다. 현재 기능은 사용자가 올린 원본 양식에 업무 데이터를 매핑하여 채우는 방식입니다.

1. **결제·마감**에서 필요한 공장·프로젝트·기간·스타일을 검색·필터합니다.
2. **을지 양식 다운로드**를 열고 실제 `.xlsx` 양식을 선택합니다. 파일은 최대 10MB이며 `.xls`·`.xlsm`·암호화된 파일은 지원하지 않습니다.
3. 사용할 시트, 머리글 행, **데이터 시작 행·마지막 행**을 지정합니다. 합계·서명란과 안내 문구를 데이터 영역에 포함하지 마세요.
4. 원본 각 열에 연결할 SIG 항목을 확인합니다. 연결하지 않은 열은 원본을 유지합니다. 단가·부가세처럼 현재 데이터에 없는 항목을 추측해 만들지 않습니다.
5. 기존 값 교체 여부와 지정 영역을 확인하고 미리보기를 대조한 뒤 **양식 채워서 다운로드**합니다.

스타일+컬러당 한 행으로, 현재 접근 권한과 필터 결과만 채웁니다. **행을 삽입하지 않고** 지정된 고정 데이터 영역 안의 연결된 열만 수정합니다. 남는 행을 비우는 옵션도 연결한 열에만 적용합니다. 다른 시트·헤더·영역 밖의 값과 지원되는 서식을 유지합니다.

데이터 영역의 병합, 연결한 열의 수식·배열/공유 수식 영역, 부족한 행 수 등 안전하게 쓸 수 없는 구조는 작업을 중단합니다. 원본 레이아웃을 억지로 바꾸지 않습니다. ExcelJS가 지원하지 않는 특수 개체·외부 연결·고급 서식은 완전 보존을 보장할 수 없으므로 다운로드 후 원본과 비교하고 Excel의 재계산·인쇄 미리보기를 확인하세요. 실제 을지 양식의 최종 인수 검증은 원본 파일을 받은 뒤 별도로 수행해야 합니다.

## 직원별 담당 공장

관리자는 **사용자 관리 → 직원 행의 담당 공장 배정**에서 승인된 활성 본사 직원·관리자에게 복수 공장을 선택하고 사유를 입력해 저장합니다. 선택을 모두 해제하면 업무 배정을 비울 수 있습니다. 배정 버전이 바뀌면 내 선택을 유지한 상태로 충돌을 안내합니다.

이 배정은 **업무 담당 구분**입니다. 본사 직원의 기존 전체 스타일 조회 권한을 제한하거나 외부 공장의 접근 범위를 넓히지 않습니다. 외부 공장 계정의 소속 공장은 기존 사용자 권한 수정에서 따로 지정합니다.

## 개인 휴가·제품 런칭·협력업체 휴가

**프로젝트 캘린더 → 일정 등록**에서 유형, 일정명, 시작일·종료일, 메모와 사유를 입력합니다. 여러 날의 일정은 종료일을 포함한 기간 전체에 표시되며 클릭하면 상세·수정·이력을 엽니다. 기존 스타일 기반 샘플·생산 일정도 함께 유지됩니다.

| 유형 | 조회 | 등록·수정 |
| --- | --- | --- |
| 개인 휴가 `private` | 본인만, 다른 관리자도 열람 불가 | 본인 |
| 개인 휴가 `hq` | 승인된 본사 구성원 | 본인·관리자 |
| 제품 런칭 `all` | 승인된 본사·공장 구성원 | 본사 구성원 |
| 협력업체 휴가 `hq` | **본사만** | 본사 구성원, 공장 지정 필수 |

외부 공장은 자신의 비공개 개인 휴가만 등록할 수 있습니다. 협력업체 휴가는 공장 계정의 캘린더·알림·변경 이력에서 제외하고 SQL RLS에서도 차단합니다. 개인 휴가의 과거 비공개 내용이 공개 범위 변경으로 유출되지 않도록 일정 전용 감사 이력에 현재·과거 공개 범위를 함께 적용합니다. 삭제는 캘린더에서 제외하는 보존 삭제입니다.

## 중화 라벨·비와이 자수

관리자 **작업 종류 관리**에서는 제공된 고정 종류의 **활성·비활성 상태만** 변경합니다. 새 종류를 추가하거나 기존 명칭·작업 구분을 바꿀 수 없습니다. 사용자 제공 목록은 라벨 23종·비와이 자수 33종이며, `src/lib/default-operation-catalogs.json`의 실제 이름을 TypeScript 로더와 003 SQL에서 사용합니다. 003 적용 시 고정 목록만 등록하고 실제 작업 주문·생산 수량은 만들지 않습니다. 임의의 새 품목을 체험 예시처럼 추가하지 않습니다.

스타일 상세의 **발주·출고·가공 → 중화 라벨 / 비와이 자수**에서 승인된 고정 종류를 선택하고 사양·상태·메모와 다음 항목을 입력합니다.

| 업무 | 수량 | 일자 |
| --- | --- | --- |
| 중화 라벨 | 발주 수량, 로스 수량, 총 필요 수량 자동 합산 | 발주일, 입고 예정일 |
| 비와이 자수 | 요청 수량, 완료 수량, 잔여 수량 자동 계산. 완료는 요청을 초과할 수 없음 | 요청일, 예정일, 완료일 |

작업 편집 화면에서도 자유 입력한 이름을 종류로 추가하지 않습니다. 사용하지 않는 종류는 관리자가 비활성화하며 이전 기록과 이름은 보존됩니다.

관리자·본사 직원이 작업 지시를 작성하고, 외부 공장은 배정된 스타일에서 허용된 범위를 조회합니다. 저장은 스타일·작업별 버전과 권한을 검사하며 변경 사유를 보존합니다.

## 실제 서비스 확인 항목

자동화 검증의 실제 결과는 [TEST_RESULTS.md](TEST_RESULTS.md)에 기록합니다. 운영 연결 후에는 다음을 별도로 확인하세요.

- 실제 오더 원본에서 품번·컬러·6사이즈를 대조하고 두 사용자 동시 편집 시 전체 가져오기가 취소되는지 확인합니다.
- PO 시험 수신인 한 명에게만 검증된 주소로 발송하여 Resend 접수 ID, 제목·본문 납기, 실제 받은 메일을 각각 대조합니다. API 접수와 수신은 별개의 결과로 기록합니다.
- 실제 을지 원본의 헤더·수식·합계·서명·인쇄 영역과 결과 파일을 비교합니다.
- 두 공장 계정으로 부분 출고·파일·스타일 배정 격리를 확인합니다.
- 본사 직원의 여러 공장 배정이 외부 공장 접근 범위에 영향을 주지 않는지 확인합니다.
- 개인 비공개 일정과 협력업체 휴가가 다른 계정의 목록·알림·이력·직접 API 응답에 노출되지 않는지 확인합니다.
- 라벨·자수 고정 종류와 수량·로스·완료·일자를 실제 현업 목록과 대조합니다.
